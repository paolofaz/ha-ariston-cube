# Ariston Cube 1.1.0-rc.6 — finite Cube S bands, 15-minute grid

**Experimental pre-release for the Cube S schedule editor.** Based on the
working 1.1.0-rc.5, not on the independent gas-hour branch.

## Requested UI fixes

### 1. Adding a band now requires BOTH start and end

The existing Lovelace weekly card now offers:
- **Inizio nuova fascia**
- **Fine nuova fascia**
- **Modalità nuova fascia:** Comfort or Economy

Both times are **required**. The previous rc.5 behavior introduced just
one start boundary, which could unintentionally extend the selected
preset until the next programmed change (sometimes as late as midnight).

Example, existing Monday:
- 00:00 Economy, 06:00 Comfort, 21:30 Economy

Add **12:00–13:00 Economy**:
- 00:00 Economy, 06:00 Comfort, **12:00 Economy**, **13:00 Comfort**,
  21:30 Economy

**At the end of the new band, the existing Comfort preset returns**, and
all pre-existing programmed boundaries remain unchanged. If the proposed
end exactly matches an already-existing boundary, that boundary itself
resumes the original programme; it is not duplicated. An end crossing an
existing boundary is refused (create separate smaller bands instead).

**A single confirmed save sends ONE POST** with the complete replacement
plans, even though a new finite interval may introduce TWO boundaries.
The backend checks that there are no overlaps, rejects missing or reversed
end times, and still verifies the entire seven-day cloud programme after
the POST. A follow-up failed/ambiguous write is never retried automatically.

**Deleting the newly inserted band's start boundary** also removes
its redundant end/restore boundary if that restores the previous
schedule; the preview shows both changes. This lets you return exactly
to the prior programme, without an extra no-op marker.

### 2. All proposed times are quarter-hour selections

For **Sposta orario** and **Aggiungi fascia**, the free-form time input
is replaced by a dropdown with 15-minute increments:

`00:15, 00:30, 00:45, 01:00, ... 23:45`.

The midnight boundary cannot be moved or inserted, and the end of a
new band cannot be unspecified or silently default to 24:00.

The backend also rejects a new time like `12:07`, including for
**existing legacy move actions**. Existing cloud times still appear
verbatim as source-boundary choices for editing/removing; the new time
must land on a quarter hour.

### Safety unchanged

- Offline preview and explicit confirmation for every operation.
- Fresh GET/fingerprint, **ONE POST**, full seven-day GET/readback.
- A confirmed change unlocks the editor for another preview **without
  closing and reopening**. An ambiguous response blocks further writes.
- No edits to cumulative gas sensors, their unique IDs, gas ledger,
  offsets, Home Assistant Recorder, or existing gas statistics.
- Stable `main` 1.0.1 and experimental gas `v1.0.2-rc.2` untouched.

## Important upgrade/testing instructions

Because **rc.5 may have created a band with no explicit end**, first
**open the official Ariston app and inspect the complete current programme**,
including the following boundary and later hours. If you already added
a band for testing, do not assume it has stopped at the intended time.

Back up the existing week (screenshots). After installing rc.6 via HACS
and restarting Home Assistant, open **Modifica fasce → Aggiungi fascia**,
choose **start, end, and preset**, select **Anteprima**, and only save
after inspecting all proposed boundaries and confirming that the original
programme resumes at end. Verify the written weekday in the Ariston app.

The example below is read-only; it never modifies the boiler:

```yaml
action: ariston_cube.preview_weekly_change
data:
  day: 1
  operation: add
  to_time: "12:00"
  end_time: "13:00"
  preset: Economy
```

Only if that preset differs from the existing interval and no real
boundary lies inside 12:00–13:00 will the preview be eligible.

The body format follows the already field-tested rc.3/rc.5
`{"plans": [...]}` schedule POST, but the two-boundary add operation
needs a deliberate real-device field test; offline CI does not prove
Ariston always accepts a two-boundary change.

**DO NOT replace rc.2 gas with rc.6 when you need the gas attribution
field test.** These are different experimental branches; switching
software does not undo Cube S programme writes.
